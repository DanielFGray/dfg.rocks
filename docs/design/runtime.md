# Runtime behavior and deployment

Production runs on the server-ansible platform (`~/build/server-ansible`), described by `cartridge.json`. A push of `main` to the control host releases: reconcile builds the Dockerfile from `main`'s committed tree, so the image never sees `.env` or `generated/`. Traefik ends TLS and sets `X-Real-Ip`, the only client-address header the rate limiter trusts. `cartridge.json` asks for Valkey, and the platform sets `VALKEY_URL` and `VALKEY_KEY_PREFIX` (`dfg-rocks:`, the only keys the app's Valkey user may touch). The platform creates `dfg_rocks_owner` and `dfg_rocks_visitor` group roles, a migration login in the owner role, and a NOINHERIT API login in the visitor role. The server prestart runs `bun run migrate`, which installs the graphile-worker schema and applies committed migrations.

The server reads each setting with Effect `Config` where it uses it. Worker tasks read `process.env`, and the graphile-worker CLI takes `DATABASE_URL` from the environment.

The server waits for both Postgres pools, and in production for Valkey (a PING), before it starts the worker or opens its port (`server/dependencies.ts`). Each retries for about 78 s, then startup fails with `DependencyUnavailable` naming it. The worker runner starts while its layer builds (`worker/worker.ts`), and a runner that cannot start stops the server. After boot, a Valkey outage does not stop the server: each rate-limit rule applies its `whenStoreDown` policy, and `/healthz` reports a worker that stopped.

The Stripe key (`STRIPE_SECRET_KEY`) is read on each request, not at boot. The plans are declared in `shared/pricing.ts`; Stripe holds their prices under the lookup keys the file names, and `bun run stripe:sync` (`scripts/stripe-sync-prices.ts`) makes Stripe match the file. The server reads the active price of each sold plan with one list call by lookup key, caches it for an hour, and answers 503 while a sold plan has no price. Checkout needs the key and the cached price id; the portal needs only the key. A missing setting answers 503 from the endpoint that needs it, and the rest of the server runs.

Stripe API version: every Stripe call sends `Stripe-Version: 2026-10-28.endive` (`stripeApiVersion` in `server/services/stripe.ts`). The webhook endpoint in Stripe must be set to the same version, and the webhook decodes event payloads in that shape. Change the constant and the endpoint together.

Stripe webhook: `POST /api/stripe/webhook` reads `STRIPE_WEBHOOK_SECRET` on each request, like the keys above; missing answers 503. It verifies the `Stripe-Signature` header over the raw body bytes (HMAC-SHA256, timestamp within 5 minutes) before any database read. An event id already in `app_private.stripe_events` answers 200 with no Stripe call. Otherwise a `customer.subscription.*` event makes one call, `GET /v1/subscriptions/{id}` at the pinned version, before its transaction opens, and the row takes that copy rather than the event's. Stripe answering 404 writes the row as `canceled`; any other failure answers 500 and records nothing, so Stripe retries. Checkout copies the payer's id into the subscription's metadata (`subscription_data[metadata][payer_id]`), which is how the webhook finds the payer. A row is overwritten only when its stored `stripe_event_created` is not newer than the event's `created`. `checkout.session.completed` is recorded and writes nothing. Each event id is inserted into `app_private.stripe_events` in the same transaction as its effect, so a redelivery changes nothing.
